# P5.2 implementation review and remediation handoff

## Status and authority

This document records the review of the P5.2 implementation commits in the
inclusive user-supplied history range `d4bec57` through `a5db4f2` on
2026-08-12. The P5.2 implementation sequence is `17c6f6d` through `fec79df`;
the preceding P5.1 work is reviewed separately in the
[P5.1 remediation review](p5.1-remediation-review.md). `2229373` is a workflow
policy change and `a5db4f2` is a broader application/UI direction change, so
neither is treated as P5.2 implementation evidence.

This is a static review and implementation handoff, not a second capability
ledger. The [implementation roadmap](../../implementation-roadmap.md) remains the
sole owner of current status and acceptance state. The
[interface specification](../../../design/interface-specification.md),
[implementation-readiness review](../../../implementation/implementation-readiness-review.md),
[Chapter 5 guide](../../../guides/chapter-5-elliptic-control.md), and
[v1 semantic compiler contract](../../../implementation/v1/semantic-compiler.md)
remain authoritative for semantics and lowering.

The selected P5.2 formulas and backend operators have landed, but P5.2 is not
acceptance-complete. Three implementation findings must be corrected:

1. `P5.2-R1` – make the weighted-trace and negative-metric realization
   selections typed, and make the executable use the declared continuous-
   control boundary;
2. `P5.2-R2` – require and record the declared $H^{1}_{0}$ target-data
   membership instead of accepting arbitrary $H^{1}$ Functions; and
3. `P5.2-R3` – expose and record the realized weighted-trace observation
   dimension instead of copying the state dimension.

The review covered:

- `17c6f6d` – full-domain $H^{1}_{0}$ state observation;
- `2d14346`, `0ea9af7`, and `79d4c8b` – weighted boundary trace semantics,
  lowering, tests, and documentation;

- `8bc9354` and `ae2f2ab` – the $L^{2}$ companion and compiled negative

The staging of the two new capabilities was generally honest:
`weighted_boundary_trace` remained explicitly non-lowerable in `2d14346`
until `0ea9af7`, and the $H^{-1}$ semantic and standalone operator commits did
not enable the compiler target before `ae2f2ab`. Preserve that staging model
for the remediation.

The remediation must preserve the behavior that static inspection found
internally consistent:

- full-domain energy tracking assembles the selected mass-plus-stiffness
  pairing for state value, desired-state load, desired-state norm, and state
  covector;
- a weighted trace represents $`O_{h}(y_{h})=h\gamma y_{h}`$ and the
  quadratic loss assembles $h^{2}$ in its state operator and $h z_{d}$ in its
  target load;
- the weighted observation does not alter the Neumann residual, facewise
  control layout, control loss, or `l2_facewise` metric;
- the continuous-control $L^{2}$ and $H^{-1}$ comparison factories use the
  same independent conforming control coordinates and produce identical
  reduced objectives and covectors;
- the negative metric applies
  $`G_{h}=M_{h}K_{h}^{-1}M_{h}`$ and its inverse applies
  $`G_{h}^{-1}=M_{h}^{-1}K_{h}M_{h}^{-1}`$;
- the selected fixed-Dirichlet policy removes the Laplacian constant mode;
- metric selection changes only direction formation; and
- no coefficientwise box is registered for the continuous-control
  comparison.

The committed tests include an independent energy-value oracle, objective
directional differences, reduced Taylor checks, exact weighted-scaling
comparisons, residual invariance checks, an independent matrix-level
$H^{-1}$ action/inverse/symmetry test, compiled $L^{2}$/$H^{-1}$ comparison,
and binding/manifest diagnostics. Those tests are valuable and must remain.

No build or test command was run during this static review. The findings come
from direct inspection of the committed semantic, compiler, model, metric,
manifest, and test code.

## P5.2-R1 – selected P5.2 realizations are not executable contracts

**Severity:** P1 – blocks P5.2 acceptance because the compiler can ignore the
declared boundary or realization while executing its built-in target.

### Evidence

The weighted trace and negative metric both depend on selected discrete
realizations, but the semantic graph represents the selections only through a
coarse kind plus `RequirementPolicySpec::selected_policy` prose.

For the weighted trace, semantic validation requires a selected
`boundary_trace` policy with a nonempty display string and a matching region.
It does not distinguish the registered `FE_Q` face-quadrature multiplication
and transpose from a nodal projection, interpolation, mass projection, or
other unregistered trace rule. The backend always evaluates the state and
weight at `QGauss` face points and assembles the matching pullback.

For the negative metric, `MetricKind::hminus1` does not carry the selected
operator $M_{h}K_{h}^{-1}M_{h}$, its inverse sequence, its nullspace policy,
or the boundary used to define $K_{h}$. The implementation-readiness review
explicitly says there is no generic $H^{-1}$ default, yet the compiler selects
the named P5.2 operator from the coarse metric kind and graph booleans.

There is also a direct boundary mismatch. The continuous-control factory adds
a selected fixed-Dirichlet requirement on the control. The helper
`has_homogeneous_dirichlet_continuous_control()` checks only the control
subject, requirement kind, selected status, and $H^{1}$ topology. For the
$L^{2}$ companion it does not require a nonempty or valid control boundary
region. The $H^{-1}$ validator requires merely some nonempty boundary region;
it does not require the selected P5.2 region or equality with the current
state boundary.

`ContinuousControlModel`, however, receives only the state
`dirichlet_boundary_ids`. When homogeneous control is enabled it constrains
the control on those state IDs, ignoring the control policy's `region_id`.
Thus a graph can declare the control fixed on another nonempty boundary and
still compile a model that fixes it on the state boundary. The manifest says
only `independent homogeneous-Dirichlet FE_Q control coefficients` and does
not expose which IDs were actually applied.

The compiler also checks only that the requested state boundary IDs occur on
the mesh. Unlike the P5.1 partition path, it does not prove complete exterior
coverage for the continuous-control comparison. On a colorized mesh whose
exterior uses IDs beyond the factory's `{0}`, the target can therefore lower
state and control spaces with only partial zero trace while the semantic graph
and manifest call them $H^{1}_{0}(\Omega)$.

### Required outcome

Add typed, backend-neutral realization selections for both P5.2 features.
Use the common trace vocabulary established by the P5.1/P5.3/P5.4 policy
repair rather than introducing P5.2-only strings.

The weighted-trace selection must identify at least:

- state-trace source and observation boundary region;
- scalar multiplication by the immutable weight datum;
- face-quadrature evaluation realization ID;
- observation pairing/weighting rule;
- transpose realization using the same trace and quadrature; and
- status and discrete scope.

The negative-metric selection must identify at least:

- primal search-space and dual-space IDs;
- metric operator ID `mass_laplacian_inverse_mass`, or an equivalent stable
  backend-neutral identifier;
- inverse operator sequence;
- mass and Laplacian pairing/operator references;
- control fixed-boundary region ID;
- nullspace policy;
- solve-policy reference for every inverse action; and
- selected discrete realization ID.

For the current registration, require the continuous-control fixed boundary
to be the same nonempty complete boundary used by the state. Pass the resolved
control boundary to the backend separately even if the two sets are equal.
This prevents a later target from silently reintroducing the same coupling.

`selected_policy` may remain a rendering of these records. It must not select
capability, and the manifest must be generated from the resolved selections.

### Implementation instructions

1. Define shared typed trace/quadrature identifiers and the bounded negative-
   metric realization payload. Keep metric semantics independent from the
   energy observation and control loss.
2. Populate the exact selections in
   `make_weighted_boundary_trace_neumann_control_problem()`,
   `make_l2_metric_h1_state_tracking_continuous_control_problem()`, and
   `make_hminus1_metric_h1_state_tracking_scalar_diffusion_reaction_problem()`.
3. Validate every referenced observation, datum, pairing, metric, operator,
   solve policy, and region. Validate status and scope; do not accept an
   arbitrary nonempty description.
4. Require the selected continuous-control boundary to exist, be nonempty,
   cover the registered exterior boundary, and match the state boundary for
   both the $L^{2}$ companion and $H^{-1}$ target.
5. Add exact diagnostics. Suggested capability names are
   `weighted_trace_realisation`, `weighted_trace_transpose_realisation`,
   `hminus1_metric_operator`, `hminus1_metric_inverse`,
   `hminus1_control_boundary`, and `hminus1_metric_solve_policy`.
6. Resolve a closed P5.2 realization before model construction. Do not switch
   on factory/problem IDs or parse a display string.
7. Change `ContinuousControlModel` construction to receive distinct resolved
   state and control boundary ID sets. Apply the control constraints from the
   latter and assert the current registration's equality in the compiler.
8. Make `Hminus1Metric` construction consume the resolved operator/solve
   selection. Unknown operator or inverse IDs must be lowerability
   diagnostics, not a fallback to $M_{h}K_{h}^{-1}M_{h}$.
9. Add structured weighted-observation and negative-metric records to the
   manifest, including exact boundary IDs and solve policies. Render existing
   prose from these records.
10. Update the interface specification, selected-policy review, and v1
    compiler document. Continue to state that no generic $H^{-1}$ metric is
    available.

### Required tests

Add table-driven semantic/compiler mutations for:

- a weighted trace selecting a nodal or projection realization;
- a weighted trace selecting a different transpose realization;
- wrong status, scope, or region on the trace realization;
- missing control fixed-boundary selection on the $L^{2}$ companion;
- an empty, missing, or different control boundary on the $H^{-1}$ target;
- a colorized mesh whose declared state/control boundary does not cover the
  complete exterior;
- an alternate negative-metric operator;
- an alternate inverse sequence or nullspace policy;
- a missing metric solve-policy reference; and
- arbitrary display-text edits that leave the typed selection unchanged.

Use a colorized mesh with at least two boundary IDs for the boundary mismatch
tests. A positive test must prove that the backend's independent control DoFs
correspond to the declared control boundary, not merely that some boundary
DoFs were removed. Assert the same IDs and realization/operator IDs in the
structured manifest.

Keep the existing exact matrix-level $H^{-1}$ oracle, symmetry/round-trip
checks, weighted objective/pullback scaling, residual invariance, equal
reduced-covector comparison, distinct direction, and Taylor tests.

## P5.2-R2 – $H^{1}_{0}$ target-data membership is not required

**Severity:** P1 – blocks P5.2 acceptance because the graph and manifest can
claim an $H^{1}_{0}$ tracking problem while the executable consumes a datum
outside that space.

### Evidence

`make_h1_state_tracking_scalar_diffusion_reaction_problem()` changes the
state-observation output topology to $H^{1}$, labels its pairing
`H1_0 state-observation pairing`, and changes the desired-state evaluation
description to `value and gradient`. The Chapter 5 guide states the selected
primary target assumption $z_{d}\in H^{1}_{0}(\Omega)$.

The factory does not add a requirement that `desired_state` has the declared
zero trace. Semantic validation checks the observation topology and the
existence of an analytic quadrature policy, but not target-data membership.
Compilation accepts any scalar deal.II `Function` with value and gradient.
For example, a nonzero constant target can compile even though it is not in
$H^{1}_{0}(\Omega)$.

The backend then computes a valid full $H^{1}$ value
$`\frac12\lVert y-z_{d}\rVert_{H^{1}(\Omega)}^{2}`$, but that is not enough to
justify the semantic $H^{1}_{0}$ target declaration or the source assumption.
The manifest records `H1_0` based on the target kind, not on a supplied
model-author membership assumption.

### Required outcome

Keep the selected $H^{1}_{0}$ formulation and require an explicit
model-author assumption that the desired-state datum belongs to the declared
space and has zero trace on the selected fixed boundary. The compiler cannot
prove this for an arbitrary analytic Function and must not claim that it has.

Use a typed requirement or data-membership payload with stable references to:

- `desired_state`;
- `state_observation_space`;
- the fixed-Dirichlet boundary region;
- $H^{1}$ value/weak-gradient availability;
- zero-trace membership; and
- continuous-semantics `user_assumed` status.

If the project instead intends to support general $H^{1}$ targets, that must
be a separately documented registration with truthful space/pairing labels.
Do not silently relabel the current source-derived factory during this repair.

### Implementation instructions

1. Add the smallest typed data-membership/zero-trace requirement needed to
   express the source assumption without pretending to prove it.
2. Populate it in the H1-state factory and therefore in both continuous-
   control comparison factories that derive from it.
3. Validate the exact datum, observation space, boundary region, status,
   scope, and zero-trace requirement.
4. Require the policy for every registered H1-state observation before
   compiler lowering. Suggested diagnostics are
   `h1_target_space_membership` and `h1_target_zero_trace`.
5. Record the supplied assumption and referenced boundary in a structured
   manifest record. Distinguish `user_assumed` from a checked property.
6. Keep value-and-gradient quadrature as a separate selected discrete data
   evaluation rule.
7. Update the guide/v1 compiler text only as needed to explain the explicit
   assumption and its provenance.

### Required tests

Add semantic mutations for a missing membership record, wrong datum, wrong
observation space, wrong boundary region, missing zero-trace selection, wrong
scope, and a falsely `provided` or `selected_discrete_realisation` status.
Each must receive one exact diagnostic.

Add compiler/manifest checks proving that all three H1-state factories carry
the same target-data assumption. Keep the existing polynomial target as the
positive numerical oracle because it has zero trace. A separate test may bind
a nonzero-trace Function only when its graph explicitly carries the
model-author assumption; the test must say that the property is assumed, not
runtime-verified.

## P5.2-R3 – weighted-trace dimensions fall through to state dimensions

**Severity:** P2 – the executable objective is correct, but structured
provenance describes the wrong realized observation space.

### Evidence

`DealiiCompiler::compiled_space_dimension()` handles point sensors specially.
For every other observation it returns the decision dimension when the input
is the decision and otherwise returns the state-variable dimension.

The weighted boundary trace consumes the state, so its
`state_observation_space` is recorded with the state dimension. That is not
the dimension of the realized map $h\gamma y$ on selected face quadrature.
The state dimension includes volume DoFs and may include constrained
Dirichlet entries; the observation acts only on the declared observation
boundary.

The current weighted backend fuses the observation and quadratic loss into a
tracking matrix/load. It has no realized observation record from which the
manifest can obtain a dimension. Existing tests check compiler IDs, binding
provenance, scaling, and general manifest structure but do not compare the
observation-space dimension with an actual weighted-trace map.

This is the same architectural defect identified for normal flux in
`P5.3-R3` and transformed state observations in `P5.4-R3`. It must use one
shared realized-space metadata path rather than another target-specific
branch in `compiled_space_dimension()`.

### Required outcome

Make the weighted trace expose one concrete realized observation map. For the
current pointwise multiplier and face-quadrature loss, the natural bounded
choice is the ordered vector of selected boundary-face quadrature samples:

```math
(C_{h}y_{h})_{f,q}=h(x_{f,q})\gamma y_{h}(x_{f,q}).
```

The observation pairing carries the matching face-quadrature weights, and
the transpose uses the exact same ordered samples and weights. Its realized
dimension is the number of selected `(boundary face, quadrature point)`
pairs. If another representation is chosen, document it and prove that its
value, pairing, transpose, and assembled quadratic loss are exactly
equivalent. Do not call the state dimension the trace dimension.

The executable/lowerer must report the realized space metadata to manifest
generation. Keep semantic dimensions unspecified for infinite-dimensional
spaces; this finding concerns the compiled realization.

### Implementation instructions

1. Introduce or reuse the common compiler-to-manifest realized-space record
   required by P5.3 and P5.4. It should contain semantic space ID, realization
   ID, dimension, layout/ordering description, and pairing realization.
2. Factor the current weighted face assembly around a stable ordered
   observation map, or construct an equivalent internal map whose value,
   JVP, and VJP can be tested independently.
3. Include weight multiplication in value and JVP and exactly one weight
   factor in the observation transpose. The quadratic loss supplies the
   second factor through its residual seed.
4. Include `JxW` in the selected observation pairing/transpose exactly once.
5. Obtain the manifest dimension from the realized observation record. Remove
   the state-dimension fallback for weighted boundary traces.
6. Keep the control observation dimension equal to the facewise control
   layout; do not conflate it with the weighted state observation.
7. Generate `observation_realisation` and the new structured space record
   from the same resolved object.
8. Update the v1 compiler document with the chosen ordering and pairing.

### Required tests

On a mesh where the state dimension differs from the number of selected face
quadrature samples, verify:

- weighted-trace value for a nonconstant state and nonconstant weight;
- JVP against a centered difference of the observation map;
- the weighted observation VJP pairing with nonuniform seeds;
- equality between the explicit observation-loss composition and the
  existing assembled objective/covector;
- residual and control-metric invariance;
- manifest dimension equal to the actual realized observation vector size;
- control-observation dimension still equal to the facewise control layout;
  and
- stable ordering across value, JVP, VJP, and manifest records.

Retain the existing constant-weight scaling test as a simple independent
oracle. Extend the shared realized-dimension test table to cover P5.2 weighted
trace, P5.3 normal flux, P5.4 transformed state observations, and ordinary
volume observations.

## Acceptance checklist

P5.2 can return to `completed` only when all of the following are true:

- [ ] weighted trace capability is selected from a typed trace, quadrature,
      pairing, and transpose realization;
- [ ] the named $H^{-1}$ operator, inverse sequence, boundary/nullspace
      policy, and solve references are typed and validated;
- [ ] the executable applies homogeneous control constraints on the boundary
      declared by the control policy;
- [ ] the manifest records the exact control boundary and negative-metric
      realization from the resolved selection;
- [ ] every H1-state factory carries the model-author $H^{1}_{0}$ target and
      zero-trace assumption with truthful status;
- [ ] weighted trace has independently testable value, JVP, and VJP actions;
- [ ] the weighted observation manifest dimension equals its actual realized
      output dimension rather than the state dimension;
- [ ] display-string edits cannot change or contradict compiler behavior;
- [ ] existing energy, weighted-scaling, residual-invariance, metric,
      equal-covector/distinct-direction, symmetry, inverse, and Taylor tests
      still pass;
- [ ] the complete neutral and deal.II Debug profiles pass; and
- [ ] the roadmap alone is updated to mark P5.2 acceptance complete.
