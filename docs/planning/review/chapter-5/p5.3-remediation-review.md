# P5.3 implementation review and remediation handoff

## Status and authority

This document records the review of the P5.3 implementation commits from
`cea5242` through `d0248fb` on 2026-08-12. It is a static review and
implementation handoff, not a second capability ledger. The
[implementation roadmap](../../implementation-roadmap.md) remains the sole owner of
current status and acceptance state. The
[interface specification](../../../design/interface-specification.md),
[theoretical formalism](../../../design/theoretical-formalism.md), and
[v1 semantic compiler contract](../../../implementation/v1/semantic-compiler.md)
remain authoritative for semantics and lowering.

The review outcome is that the C5.8 normal-flux and C5.10 point-sensor code has
landed. The initial review recorded three implementation findings, and the
bounded remediation is now acceptance-complete:

1. `P5.3-R1` – make the strong/very-weak transposition declaration complete,
   structured, and validated;
2. `P5.3-R2` – prevent P5.3 targets from compiling with incomplete or
   inconsistent homogeneous-Dirichlet boundaries; and
3. `P5.3-R3` – record the actual normal-flux observation dimension in the
   structured compilation manifest.

The review also found one commit-integrity problem, `P5.3-R4`. It does not
require history rewriting without explicit user authorization, but it governs
how the remediation work must be divided.

## Review scope and retained behavior

The review covered the semantic factories and validation, scalar lowering
plan, deal.II compiler and assembled scalar model, focused semantic/deal.II
tests, manifest records, and P5.3 documentation. It did not review unrelated
Chapter 5/6 targets.

The remediation must preserve the bounded choices that are already explicit:

- point sensors use ordered, finite, unique physical coordinates;
- the point map evaluates `FE_Q` shape functions at those coordinates and
  uses the assembled finite-dimensional transpose $C_{h}^{\mathsf{T}}$;
- normal flux uses $\nabla y_{h}\mathbin\cdot n_{\mathrm{out}}$ at selected
  `FEFaceValues` quadrature points;
- the normal-flux VJP includes the same face-quadrature weights as the loss;
- nearest-node and quadrature-coincidence sensor policies remain unsupported;
- an $H(\mathrm{div})$ flux realization and a general transposition lowerer
  remain unsupported; and
- solvers remain unaware of the PDE or observation name.

Static inspection found the final value/JVP/VJP assembly internally
consistent, including the weighted normal-flux transpose. `git diff --check`
passed for the reviewed range. No build or test command was run during the
read-only review.

## P5.3-R1 – incomplete and unvalidated transposition declaration

**Severity:** P1 – blocks P5.3 acceptance.

### Evidence

P5.3 requires a formulation policy that declares the strong space $Y$, the
isomorphism $T:Y\rightarrow H$, the residual codomain, the multiplier space,
and the model-author regularity assumption. The normal-flux factory in
[`reference_specs.hpp`](../../../../include/nmopt/semantic/v1/reference_specs.hpp)
currently adds a prose `RequirementPolicySpec` that names $Y$ and a very-weak
adjoint, but does not declare $T$ or all required spaces. The point-sensor
factory includes more of the formula in prose, but the fields are not
structurally represented.

[`SemanticValidator`](../../../../include/nmopt/semantic/v1/validation.hpp) accepts
these policies when a matching requirement is present and
`selected_policy` is nonempty. The deal.II lowerability checks then recognize
selected English substrings such as `very weak` and `FE_Q shape functions`.
Consequently:

- a policy can omit $T$, the residual codomain, or the multiplier space and
  still validate;
- a prose edit can accidentally change compiler behavior;
- referenced spaces and pairings cannot be checked for closure; and
- the manifest can repeat a description without proving that the compiled
  lowerer selected the declared formulation.

There is also an operator-provenance mismatch to resolve. The roadmap renders
$T=-\Delta+rI$, while the factory and compiler accept a positive diffusion
binding and assemble $-\kappa\Delta+rI$. The implementation must not continue
to accept $\kappa\ne1$ while recording the unit-diffusion operator.

### Required semantic outcome

Add a structured, backend-neutral representation for the selected
transposition policy. The exact C++ type name is an architectural choice and
must be recorded in the interface specification and v1 compiler document, but
the representation must contain stable fields for:

- policy ID and subject equation ID;
- strong operator domain/test space $Y$;
- operator/range space $H$;
- selected isomorphism $T:Y\rightarrow H$;
- residual codomain;
- multiplier space;
- associated observation ID and transpose-source space;
- model-author domain-regularity requirement; and
- selected discrete realization ID.

The recommended bounded design is a typed transposition payload referenced by
the existing requirement policy. Keep `selected_policy` only as a
human-readable rendering. Do not parse it to establish capability.

The structured declaration must make the following relationships checkable:

```math
E:Y\times U\rightarrow H,
\qquad
p\in H,
\qquad
T^{\ast}:H\rightarrow Y^{\ast},
\qquad
C^{\ast}:Q^{\ast}\rightarrow Y^{\ast}.
```

Here $C$ is the selected point-sensor or normal-flux observation. If the
existing weak `FE_Q` state solve remains the selected discrete realization,
represent and validate its relationship to this strong parent explicitly. Do
not leave the ordinary $H^{1}$ residual as the only semantic equation while a
detached prose policy claims a different codomain and multiplier.

For the current scalar diffusion-reaction factories, prefer recording

```math
T=-\kappa\Delta+rI:Y\rightarrow L^{2}(\Omega),
\qquad
Y=H^{2}(\Omega)\cap H^{1}_{0}(\Omega),
```

because that matches the operator already assembled from the bound diffusion
and reaction data. If the intended bounded target is instead normalized unit
diffusion, restrict the accepted data and update the guide and roadmap in the
same work unit. Do not leave the current semantic/executable mismatch.

The continuous policy may remain a parent declaration for a target-specific
discrete transpose. It does not require a general transposition lowerer, but
the compiler must record exactly how the selected `FE_Q` realization relates
to the continuous spaces and operator.

### Implementation instructions

1. Add the smallest typed semantic representation that carries every field
   above. Avoid PDE-name fields or solver options.
2. Make both P5.3 reference factories populate the same structured contract,
   differing only in their observation and transpose-source realization.
3. Validate referenced IDs, space roles/topologies, equation ownership,
   policy scope/status, and observation-policy compatibility.
4. Add exact analytical-policy diagnostics for each missing or incompatible
   field. Suggested capability names are:
   `transposition_strong_space`, `transposition_isomorphism`,
   `transposition_residual_codomain`, `transposition_multiplier_space`, and
   `transposition_observation_source`.
5. Make `DealiiScalarLoweringPlanner` copy structured policy data into the
   bounded plan. Reject unknown operator or realization IDs; do not select a
   lowerer from display text.
6. Make `DealiiCompiler` compare the structured selection with the bound
   scalar operator and chosen observation. Return a lowerability diagnostic
   for an unsupported alternative.
7. Add a structured transposition record to `CompilationManifest`, or an
   equivalently typed record, and populate it from the resolved lowering
   decision. Human-readable assumptions may remain as a rendering of this
   record.
8. Update the interface specification and v1 compiler document with the
   selected structure and its bounded discrete equivalence. Keep the general
   transposition lowerer explicitly excluded.

### Required tests

Extend the backend-neutral semantic scenario to verify both factories' exact
structured policy fields. Mutate one required field at a time and require the
exact diagnostic named for that field. At minimum, cover:

- missing strong space;
- wrong or absent isomorphism;
- wrong residual codomain;
- wrong multiplier space;
- observation/policy mismatch;
- missing domain-regularity assumption; and
- a display-string change that does not alter capability resolution.

Extend the deal.II compiler scenario to verify:

- the structured operator agrees with the bound diffusion/reaction data;
- an unsupported structured realization is rejected before model
  construction; and
- the manifest record contains the exact semantic policy ID, spaces,
  operator, observation source, and discrete transpose realization.

The existing point-sensor and normal-flux value/JVP/VJP and dual-residual
checks must continue to pass. Add an objective directional-difference check
and a state-recomputed reduced Taylor check for each P5.3 target. Use a
nonzero observation mismatch so the low-regularity transpose contributes to
the derivative under test.

## P5.3-R2 – incomplete and inconsistent Dirichlet boundary selection

**Severity:** P1 – can silently compile a different PDE.

### Evidence

`make_normal_flux_scalar_diffusion_reaction_problem()` accepts arbitrary
normal-flux boundary IDs but independently hard-codes the fixed-Dirichlet
region to `{0, 1}`. On a mesh with boundary IDs `{0, 1, 2}`, a call selecting
normal-flux ID `{2}` can pass the current presence checks while leaving the
observed boundary unconstrained. Even the default `{1}` selection accepts a
colorized mesh with additional exterior IDs, leaving those faces with the
natural boundary condition.

The compiler currently calls `contains_all_boundary_ids()`, which proves only
that every requested ID occurs on the mesh. It does not prove that the fixed
Dirichlet region covers every exterior face. The positive normal-flux test
avoids the failure by assigning ID `1` to the observed side and collapsing
every other exterior face to ID `0`.

The point-sensor factory inherits the base fixed region `{0}` and has the same
full-boundary risk on a mesh with multiple exterior IDs. Both C5.8 and C5.10
declare homogeneous Dirichlet data on the complete boundary.

### Required semantic and compiler outcome

Make fixed and observed boundary selections independent explicit inputs. A
source-compatible bounded signature is:

```cpp
make_point_sensor_scalar_diffusion_reaction_problem(
  sensor_coordinates,
  fixed_dirichlet_boundary_ids = {0});

make_normal_flux_scalar_diffusion_reaction_problem(
  normal_flux_boundary_ids = {1},
  fixed_dirichlet_boundary_ids = {0, 1});
```

Equivalent overloads are acceptable. Do not infer all exterior mesh IDs in
the semantic factory; the semantic graph must own its intended fixed region.

Implement the following invariants:

1. Every fixed-boundary ID list is nonempty and duplicate-free; the
   normal-flux observation list is also nonempty and duplicate-free.
2. Every normal-flux observation ID belongs to the declared fixed-Dirichlet
   region.
3. For the registered P5.3 targets, every exterior mesh face belongs to the
   fixed-Dirichlet region.
4. The compiler rejects an absent requested ID and separately rejects an
   undeclared exterior ID.
5. The assembled constraints use exactly the fixed IDs that passed these
   checks.

Reuse the existing complete-exterior-boundary traversal rather than adding a
PDE-name branch to the scalar model. Keep the lowerability check in the
compiler because semantic validation cannot inspect a concrete mesh.

Suggested diagnostics are:

- structural `normal_flux_fixed_boundary_subset` when an observed ID is not
  fixed; and
- lowerability `p53_complete_fixed_dirichlet_boundary` when a concrete mesh
  contains an exterior face outside the declared fixed region.

### Required tests

Add focused cases for:

- the existing default meshes;
- a colorized or manually labeled mesh whose complete fixed set is declared;
- a custom normal-flux boundary ID other than `1` that is also fixed;
- a normal-flux observation ID omitted from the fixed region;
- an extra exterior mesh ID omitted from the declared fixed region for C5.8;
  and
- the same incomplete fixed-boundary failure for C5.10.

The negative cases must assert diagnostic category, component ID, capability,
and remedy. At least one positive custom-ID case must solve the manufactured
state and verify the normal-flux value, so the test proves the constraints and
observation use the same declared boundary.

## P5.3-R3 – incorrect compiled normal-flux observation dimension

**Severity:** P2 – corrupts structured provenance and downstream tooling.

### Evidence

`compiled_space_dimension()` special-cases `point_sensor`, whose finite
dimension comes from the semantic point count. A normal-flux observation falls
through to the generic state-observation branch and receives the state-vector
dimension. The executable normal-flux map instead produces one coefficient
for each selected boundary-face quadrature point.

The mismatch means `CompilationManifest::spaces` disagrees with
`normal_flux_values()` and `normal_flux_jvp()`. The manifest is explicitly the
structured input used by experiment tooling, so a descriptive observation
string is not an adequate substitute.

### Required implementation outcome

Carry the realized observation dimension from the concrete lowerer into
manifest construction. Prefer obtaining the count from the assembled
normal-flux operator after construction rather than recomputing face and
quadrature counts in `make_manifest()`.

A narrow implementation may:

1. add a const `normal_flux_observation_dimension()` accessor to the concrete
   scalar component model;
2. capture the value while the compiler still owns the typed model pointer;
3. pass an optional realized observation-dimension record into
   `make_manifest()`; and
4. require `compiled_space_dimension()` to use it for the matching semantic
   observation space.

Do not add a `dynamic_cast` from the generic executable merely to construct
metadata. If a general executable observation-layout port is proposed instead,
that is a larger public-interface decision and must be documented before
implementation.

### Required tests

In the normal-flux deal.II scenario, find the `CompiledSpaceRecord` for
`state_observation_space` and require that its dimension equals both
`normal_flux_values().size()` and `normal_flux_jvp(...).block(0).size()`.
Retain the point-sensor assertion that the same record equals the declared
point count. Add a negative internal contract check if manifest construction
is given a realized dimension for the wrong observation ID.

## P5.3-R4 – dishonest intermediate commit boundary

**Severity:** P2 – history/process finding; final `HEAD` contains the later
assembly.

Commit `d1bf96b` makes normal-flux graphs lowerable and labels their manifest
as `normal_flux`, but the concrete scalar model at that commit still assembles
the pre-existing volume-tracking observation. Commit `4dc91ae` adds the actual
normal-flux operator. A checkout or bisect at `d1bf96b` therefore compiles a
graph to behavior that contradicts its semantic observation and manifest.

Do not rewrite these commits unless the user explicitly authorizes history
rewriting. For the remediation work, every commit that makes a semantic graph
lowerable must include the concrete value/JVP/VJP realization and its focused
tests. If routing and assembly cannot form honest independent states, keep
them in the same commit.
