  separate components; and

## P5.4-R1 – unregistered Section 5.11 cross-products can compile

**Severity:** P1 – blocks P5.4 acceptance and can make the structured manifest
contradict the executable objective.

### Evidence

The three complete-boundary Section 5.11 factories deliberately register
three distinct compositions:

| Registration | State tracking | Control loss | Search metric |
| --- | --- | --- | --- |
| Section 5.11.1 option 1 | volume $L^{2}$ | $H^{1/2}(\Gamma)$ | $H^{1/2}(\Gamma)$ |
| Section 5.11.1 option 2 | volume $H^{1}$ | $L^{2}(\Gamma)$ | $H^{1/2}(\Gamma)$ |
| Section 5.11.3 | volume $L^{2}$ | tangential $H^{1}(\Gamma)$ | tangential $H^{1}(\Gamma)$ |

`DealiiCompiler` does not match these complete signatures. It derives
independent booleans from the presence of an $H^{1}$ state observation, an
$H^{1/2}$ or $H^{1}$ loss, and the selected metric kind. The target selection
then classifies a normalized Dirichlet graph in this order:

1. an $H^{1}$ control loss selects the tangential target;
2. otherwise an $H^{1}$ state observation selects option 2; and
3. otherwise the graph is labeled option 1.

The graph-wide lowerability check verifies the number of residual terms,
losses, observations, and metrics, but it does not verify the registered
relationship among their kinds. In particular,
`registered_h1_dirichlet_tracking` is true for any normalized graph with an
$H^{1/2}$ metric and no $H^{1}$ control loss. It does not require the selected
$L^{2}(\Gamma)$ control loss.

Consequently, a mutation of the option-1 factory from $L^{2}$ state tracking
to $H^{1}$ state tracking can remain semantically valid and lowerable while
retaining the $H^{1/2}$ control loss. The compiler executes this unregistered
hybrid but labels it as option 2. The manifest then claims an
$L^{2}(\Gamma)$ control loss even though
`DirichletControlLiftingModel` applies the fractional loss. The reverse
mutation can similarly produce an $L^{2}$ state loss and $L^{2}$ control loss
with an $H^{1/2}$ search metric while the target and manifest claim option 1.
Other adjusted loss/metric/topology combinations can create the same split
because model construction uses specification booleans while manifest
construction re-derives behavior from `CompiledTargetKind`.

This violates the v1 rule that only explicitly registered combinations lower
and that the manifest describes the executable computation.

### Required outcome

Resolve one closed P5.4 registration signature before constructing the
backend model. The resolver must distinguish at least:

- complete-boundary nodal $L^{2}$ lifting for the pre-P5.4 target;
- partial fixed/controlled nodal $L^{2}$ lifting;
- the Chapter 5.11.2 $L^{2}$ transposition parent with conforming trace
  equivalence;
- Section 5.11.1 option 1;
- Section 5.11.1 option 2; and
- Section 5.11.3 tangential $H^{1}$ control.

The signature must be determined from typed component structure, not the
factory or problem identifier. It must include:

- residual formulation and transformation kind;
- complete or partial boundary policy;
- continuous state, test, control, and observation topologies;
- state observation kind;
- control observation topology and pairing;
- control-loss kind;
- selected search-metric kind; and
- the required trace, equivalence, interface, and metric-realization
  selections from `P5.4-R2`.

Any structurally valid graph that is not one of these registrations must
receive a lowerability diagnostic. The compiler must not assemble the nearest
combination.

### Implementation instructions

1. Introduce a private closed result such as
   `DirichletControlRegistration` and a resolver that consumes the resolved
   semantic graph. Keep it in the compiler layer; it is a lowering decision,
   not a new semantic PDE kind.
2. Build the registration from exact typed ports and selected policies. Do
   not switch on `specification.id`, labels, or rendered policy prose.
3. Return one exact diagnostic, such as
   `section_5_11_registered_signature`, when a normalized Chapter 5.11 graph
   does not match a registered signature. The remedy should name the allowed
   state-tracking/loss/metric triples.
4. Use the resolved registration as the single input for:
   - `DirichletObjectivePolicy` construction;
   - concrete metric construction;
   - `CompiledTargetKind` selection;
   - compiler ID and control-space rendering; and
   - structured and human-readable manifest records.
5. Remove or narrow independent boolean recomputation where it can disagree
   with the resolved registration. Ordinary feature predicates may remain for
   diagnostics that do not select executable behavior.
6. Add semantic topology checks for the tangential $H^{1}$ control loss and
   metric comparable to the existing $H^{1/2}$ checks. These local checks do
   not replace the complete compiler signature match.
7. Document the closed registration table in the v1 compiler contract and
   retain all excluded cross-products explicitly.

### Required tests

Add table-driven mutation tests beginning from the valid factories. Each
mutation must remain structurally meaningful and then receive the exact
lowerability diagnostic rather than compiling to another target. At minimum,
cover:

- option 1 with $H^{1}$ state tracking but the fractional control loss;
- option 2 with $L^{2}$ state tracking while retaining its $L^{2}$ loss and
  fractional search metric;
- option 1 with an $H^{1}$ metric or tangential policy;
- Section 5.11.3 with a fractional metric;
- a control-loss observation space whose topology disagrees with the loss;
  and
- a valid graph whose `id` and labels are changed, proving structural rather
  than name-based registration.

For every valid factory, assert that the resolved registration, objective
policy, concrete metric ID, compiler ID, metric manifest record, state
observation record, and control-loss assumption all identify the same
variant. Keep the existing nonzero-mismatch Taylor and stationarity tests.

## P5.4-R2 – trace, interface, and transposition policies are not executable contracts

**Severity:** P1 – blocks P5.4 acceptance because the compiler can silently
substitute its built-in policy for a different declaration.

### Evidence

The factories add `RequirementPolicySpec` records for the boundary partition,
fixed-interface ownership, conforming trace subspace, transposition
equivalence, fractional trace realization, tangential-gradient realization,
and discrete conormal. Most capability checks establish only a subject,
requirement kind, selected status, and nonempty `selected_policy` string.

The gaps are observable:

- removing `partial_dirichlet_boundary_partition` does not invalidate the
  partial semantic graph or the deal.II graph; the compiler independently
  inspects region ID sets and never requires that policy;
- the partial interface check accepts any selected
  `controlled_dirichlet` policy on `dirichlet_control_lifting`, including an
  empty description, the wrong scope or region, or an alternate ownership
  rule, while the backend always applies fixed-data precedence;
- the $H^{1/2}$ and tangential $H^{1}$ validators require a nonempty policy of
  the expected kind but do not distinguish the selected Schur-complement and
  projected-gradient realizations from unsupported alternatives; and
- the Chapter 5.11.2 transposition formulation, domain assumption, conforming
  subspace, and conormal are still prose payloads. Their IDs and mathematical
  relationships cannot be checked, and the lowerer cannot prove that the
  declared equivalence is the one it executes.

The manifest appends every policy string after model construction. Repeating
the declaration is provenance only; it does not demonstrate that the
compiled realization matched it.

### Required semantic outcome

Use typed, backend-neutral selections for the policies that determine P5.4
behavior. The smallest acceptable design may use typed payloads referenced by
existing requirement records, but it must make the following information
machine-checkable.

For partial Dirichlet lifting, record:

- fixed and controlled boundary-region IDs;
- complete exterior coverage and disjointness requirements;
- interface ownership, currently fixed-data precedence;
- the controlled trace rule, currently relative-interior nodal coordinates
  with zero endpoint extension; and
- the hanging/interface relation policy, currently unsupported and rejected.

For the fractional metric, record:

- the control and volume space IDs;
- the trace inclusion $U_{h}=\mathrm{tr}_{\Gamma}V_{h}$;
- the volume operator $A_{h}=M_{\Omega,h}+K_{\Omega,h}$;
- minimum-$H^{1}$ extension as the apply policy;
- the full-volume inverse boundary block as the inverse policy; and
- the solve-policy port used by both actions.

For the tangential metric, record:

- the control and boundary-region IDs;
- $M_{\Gamma,h}+K^{\tau}_{\Gamma,h}$ as the Riesz operator;
- facewise projection of ambient gradients onto the tangent space; and
- the constant-mode policy supplied by the positive mass term.

For Chapter 5.11.2, use the same structured transposition representation
required by `P5.3-R1`. It must additionally record the continuous
$L^{2}(\Gamma)$ parent, the conforming discrete trace subspace, the
variational/transposition equivalence, and the lifting-pullback conormal. Do
not create a second incompatible transposition schema for P5.4.

Keep `selected_policy` as a human-readable rendering only. Changing display
text must not alter validation or lowerer selection.

### Implementation instructions

1. Coordinate this work with
   [`P5.3-R1`](p5.3-remediation-review.md#p53-r1--incomplete-and-unvalidated-transposition-declaration).
   Add one shared typed transposition contract and populate it for C5.8,
   C5.10, and Chapter 5.11.2.
2. Add the smallest typed boundary-lifting and trace-realization selections
   needed for the fields above. Record any new semantic shape in the interface
   specification and v1 compiler document in the same work unit.
3. Make `SemanticValidator` require the partial boundary-partition record and
   validate its referenced regions, status, scope, coverage intent, interface
   owner, and trace rule.
4. Make the compiler compare the typed partial policy with the actual mesh
   boundary IDs. Keep the existing exact mesh checks for presence,
   disjointness, and complete exterior coverage.
5. Make semantic validation reject missing or incompatible fractional and
   tangential fields. Make compiler validation reject a typed but unsupported
   realization before constructing `DirichletControlLiftingModel`.
6. Carry the resolved typed selections into the private registration from
   `P5.4-R1` and into typed manifest records. Render descriptive assumptions
   from those records after successful lowering.
7. Remove all policy-string parsing or presence-only checks that grant these
   capabilities. Existing prose may remain for logs and documentation.

Suggested diagnostic capabilities are:

- `partial_dirichlet_partition_policy`;
- `partial_dirichlet_interface_selection`;
- `partial_dirichlet_trace_selection`;
- `hhalf_metric_realisation_selection`;
- `boundary_h1_metric_realisation_selection`; and
- the structured transposition diagnostics already specified by `P5.3-R1`.

### Required tests

Extend the backend-neutral semantic scenario with exact negative tests for:

- a missing partial boundary-partition policy;
- a fixed/controlled region mismatch;
- controlled precedence or zero-endpoint extension replaced by an
  unsupported choice;
- wrong policy status or scope;
- an unsupported fractional trace realization;
- an unsupported tangential-gradient realization; and
- every missing or mismatched Chapter 5.11.2 transposition field required by
  the shared P5.3 contract.

Extend the deal.II tests to verify that:

- a display-string-only change preserves the selected realization;
- a typed alternate interface, fractional, tangential, or transposition
  selection is rejected before model construction;
- the partial boundary record agrees with the actual mesh partition;
- structured manifest records contain the selected policy IDs and realized
  operator choices; and
- the retained reconstruction, metric, stationarity, and Taylor contracts
  still pass for every valid factory.

## P5.4-R3 – transformed state-observation dimensions are misreported

**Severity:** P2 – executable arithmetic is unaffected, but structured
provenance describes the wrong observation layout.

### Evidence

`compiled_space_dimension()` assigns an observation output the decision
dimension when it observes the decision and otherwise assigns the independent
state-variable dimension. This fallback is wrong for every reviewed
Dirichlet-control state observation.

`DirichletControlLiftingModel` stores the state variable in independent
homogeneous coordinates, but the state observation consumes the reconstructed
physical vector:

```math
y_{\mathrm{phys},h}
=P_{h}\widehat y_{h}+\ell_{0,h}+L_{D,h}u_{h}.
```

The physical `FE_Q` vector includes controlled boundary DoFs and, for the
partial target, fixed boundary DoFs. Its dimension is therefore larger than
the state block returned by `variable_layout()`. The objective assembly uses
the full physical mass or mass-plus-stiffness matrix, while the manifest
records the smaller independent state dimension for
`state_observation_space`.

The Section 5.11 manifest test added in `d752a91` checks IDs and descriptive
substrings but never checks `CompiledSpaceRecord::dimension`, so the mismatch
is not detected. This is the transformed-observation counterpart of the
normal-flux dimension issue in `P5.3-R3` and should use the same realized-space
metadata path.

### Required outcome

Populate observation-space dimensions from the concrete lowerer that owns the
realized map. For every P5.4 state observation, the structured dimension must
equal the physical reconstructed observation layout. The control-observation
dimension must continue to equal the independent trace-control layout.

Do not change the semantic state-variable record to the physical dimension:
the independent variable coordinates and the transformed observation output
are different runtime layouts. Do not infer either one from the other.

### Implementation instructions

1. Implement this through the same realized-space metadata path chosen for
   `P5.3-R3`. Prefer a lowerer-produced space catalog or a narrow private
   accessor over more role-based guesses in `make_manifest()`.
2. Let `DirichletControlLiftingModel` report the physical state-observation
   dimension without exposing a broad public observation API solely for
   metadata.
3. Pass the realized dimensions to manifest construction together with the
   resolved registration from `P5.4-R1`.
4. Keep state-variable, state-test/adjoint, control, state-observation, and
   control-observation dimensions separate and assert each one.
5. Update the v1 manifest documentation to state that transformed observation
   records describe the post-transformation output layout.

### Required tests

For the partial target, Chapter 5.11.2, and all three remaining Section 5.11
registrations, locate manifest space records by semantic ID and require:

- `state_space.dimension` equals the independent state block dimension;
- `state_test_space.dimension` equals the test/adjoint block dimension;
- `control_space.dimension` equals the independent trace-control dimension;
- `state_observation_space.dimension` equals
  `reconstruct_physical_state(...).size()`; and
- `control_observation_space.dimension` equals the trace-control dimension.

Use a mesh for which physical and independent state dimensions differ, and
assert that the state-observation dimension does not equal the independent
state dimension. This prevents a vacuous regression test. Integrate the same
helper with the P5.3 point/flux dimension assertions where practical.
