# P6.1 implementation review and remediation handoff

## Status and authority

This document records the completed static review of the P6.1 implementation
commits after `codex/main` on 2026-08-16. The inclusive review range is
`ff773d5` through `de4dd2f`: 22 linear commits covering the initially selected
P6.1 slice and every implementation recorded in its extension ladder.

This is review evidence and a remediation handoff, not a second capability
ledger. The [implementation roadmap](../../implementation-roadmap.md) remains
the sole owner of current feature status and acceptance state. The
[Chapter 6 numerical-methods guide](../../../guides/chapter-6-numerical-methods.md),
[v0 executable contract](../../../implementation/v0/executable-contract.md),
and [interface specification](../../../design/interface-specification.md)
remain authoritative for method semantics and executable boundaries.

The history establishes most of the intended implementation breadth: typed
direction and line-search policies, nonlinear CG variants, full and limited
memory BFGS, exact linear-quadratic Hessian providers, reduced Newton-PCG,
selectable stopping reports, and Cauchy/truncated-CG trust-region
globalization. P6.1 is not acceptance-complete from the reviewed state. Four
P1 implementation defects and three P2 evidence or edge-policy gaps remain.
One defect found at the earlier review boundary was resolved later in the same
history.

The following behavior is consistent with the selected P6.1 contracts and
should be retained:

- reduced derivatives remain covectors and search directions remain primal;
- steepest descent forms $d=-G^{-1}j_h'$ through the declared metric;
- PR+, Fletcher–Reeves, and strict quadratic CG retain typed history and
  deterministic restart behavior;
- full and limited memory BFGS use primal displacements, covector differences,
  declared curvature resets, and the metric inverse as their base inverse;
- `ReducedHessianT` is an explicit optional capability rather than an implied
  consequence of first-order DTO ports;
- the dense, direct deal.II, and compiled scalar Hessian implementations use
  tangent-state and incremental-adjoint actions without assembling a dense
  reduced Hessian;
- Newton-PCG and trust-region truncated CG keep primal/covector roles and use
  the inverse metric as a preconditioner;
- Armijo, weak-Wolfe, and strong-Wolfe acceptance use the actual returned
  displacement;
- final DTO evaluations, absolute/relative gradient histories, accepted step
  data, trust-region trial diagnostics, and action counts are represented as
  separate result fields; and
- projected trust-region steps, generic nonlinear Hessians, and the Chapter 6
  benchmark harness remain outside P6.1 rather than being inferred silently.

## P6.1-R1 – unsupported projected advanced directions are public

**Severity:** P1 – the public solver boundary executes combinations that the
P6.1 scope explicitly excludes.

### Evidence

`ReducedSearchSolverT` is templated on both direction and line-search policy,
but its two constraint-taking constructors are available for every policy.
The aliases for PR+, Fletcher–Reeves, classical quadratic CG, full and limited
memory BFGS, Newton, and exact-search combinations all reuse this class. No
policy capability check gates constrained construction.

The roadmap nevertheless declares projected steepest descent to be the only
selected projected method and records advanced projected directions as a
lower-priority extension. The implementation does not enforce that boundary.

This is not only an exposure mismatch. In the constrained branch the stopping
quantity is formed by projecting `control + direction` and measuring the
returned update. It equals the declared metric projected-gradient residual

```math
u-\Pi_{U_{\mathrm{ad}}}(u-G^{-1}j_h')
```

up to sign only for the steepest direction. With nonlinear-CG, BFGS, or
Newton directions, the solver measures a different policy-dependent map and
can report the wrong stationarity condition. Committed projected tests
instantiate the steepest-descent alias only.

### Required outcome

Make projection support an explicit public capability. The bounded repair is
to make the constraint-taking constructors available only when the direction
and line-search combination has deliberately selected projection semantics.
At present that means steepest descent with an actual-displacement Armijo or
Wolfe policy. Alternatively, reject every unselected policy with one typed,
stable diagnostic before evaluation begins.

Do not make projected nonlinear CG, BFGS, Newton, exact quadratic search, or
trust-region methods appear supported by changing only the stopping residual.
Those methods remain excluded until their active-set transition, restart,
metric-coupling, and acceptance contracts are selected and tested.

### Required tests

- preserve projected steepest-descent convergence and the declared metric
  projected-gradient residual;
- reject constrained construction or execution for every currently exposed
  advanced direction family and for exact quadratic search;
- exercise actual-displacement Armijo/Wolfe projection where it is intended;
  and
- prove that a new unconstrained direction alias does not acquire projection
  support automatically.

## P6.1-R2 – BFGS action accounting lacks an independent oracle

**Severity:** P2 – the implementation shape was corrected, but the declared
work report is not protected by callback-level evidence.

### Evidence

At `965ea21`, every direction evaluation added one metric action even though
an accepted L-BFGS secant update calls `metric.inverse_apply()` twice: once to
form the metric gradient and once inside the two-loop recursion. For $n$
successive directions without a reset, the implementation executed $2n-1$
inverse actions but reported $n$.

`bddad18` repairs the data flow. Each direction now reports its own metric and
Hessian actions; an accepted BFGS pair reports two inverse-metric actions,
while initial and reset directions report one. Full-memory BFGS later adopts
the same shape.

The final tests do not instrument `MetricT::inverse_apply()` and do not assert
the accumulated metric count for either BFGS solver. They test convergence,
descent, history retention, monotonic objectives, and curvature reset status.
The arithmetic repair can therefore regress independently of those tests.

### Required outcome and tests

Retain per-direction action accounting and add an instrumented metric that
independently proves, for both BFGS policies:

- one inverse action for the initial direction;
- two inverse actions after accepting a secant pair;
- one inverse action on a curvature reset;
- exact accumulation across several accepted pairs; and
- no hidden action-count change when L-BFGS evicts its oldest pair.

Also add L-BFGS-specific eviction and history-layout rejection tests. Those
declared behaviors are not directly covered in the reviewed state.

## P6.1-R3 – Newton inverse-metric under-count was resolved

**Severity:** P1 at introduction; resolved in the reviewed history.

### Evidence and resolution

At `bddad18`, `NewtonDirectionPolicyT::next()` invoked the metric inverse once
inside `make_metric_gradient()` and a second time to precondition the initial
PCG residual, but initialized `metric_solve_count` to one. A solve with $k$
PCG iterations executed $k+2$ inverse actions and reported $k+1$.

`4a96977` initializes the count to two, adds one for each subsequent
preconditioned residual, and introduces per-direction
`ReducedHessianSolveDiagnostics`. Its regression asserts

```math
N_G=2N_{\mathrm{direction}}+N_H
```

and matches reported PCG iterations to Hessian actions. The final
implementation now has the correct count for the stated algorithm. An
instrumented callback oracle would still strengthen this evidence, but the
specific off-by-one defect is closed and is not carried into the remediation
checklist.

## P6.1-R4 – inner tolerances can return a zero nonconverged outer step

**Severity:** P1 – valid public parameter combinations do not produce a typed
stop, failure, or usable second-order step.

### Evidence

Newton defines its PCG target as

```math
\max(\varepsilon_{\mathrm{abs}},
     \varepsilon_{\mathrm{rel}}\lVert j_h'\rVert_{G^{-1}}).
```

It initializes the Newton direction to zero and skips PCG when the initial
residual already meets that target. If the outer gradient tolerance is
smaller than the current norm but the inner absolute tolerance is larger, the
outer solver has not converged and the direction is still zero. The generic
outer descent assertion then throws `Reduced gradient did not produce a
descent direction` rather than reporting a Newton-specific outcome.

`ac27362` introduces the same boundary in truncated-CG trust-region solves.
When its initial residual meets the subproblem tolerance, it returns a
`converged` zero step with zero predicted reduction. The outer trust-region
loop divides the actual reduction by zero, rejects the non-finite ratio, and
eventually reports a radius/trial failure. Neither solver validates the
relationship between outer and inner absolute tolerances.

### Required outcome

Define one consistent second-order stagnation policy. A repair may reject
incompatible outer/inner tolerances before evaluation, return a typed
inner-solve outcome that the outer method handles deliberately, or use a
forcing policy that guarantees a nonzero step whenever the outer criterion is
not met. A trust-region subproblem must never return `converged` with zero
predicted reduction for a nonstationary outer iterate.

### Required tests

- initial residual below both outer and inner tolerances;
- residual below the Newton inner absolute tolerance but above the outer
  tolerance;
- the analogous truncated-CG trust-region mismatch;
- exact typed stop or diagnostic for each mismatch; and
- ordinary multi-iteration Newton and truncated-CG convergence after the
  repair.

## P6.1-R5 – exact quadratic search can accept a non-exact trial

**Severity:** P1 – an accepted result can violate the defining exact-search
contract and report a step length that does not describe its control update.

### Evidence

`ExactQuadraticLineSearchPolicyT` computes

```math
\tau=-\frac{j_h'[d]}{\langle H d,d\rangle}
```

from the nominal direction, then passes $\tau$ to the generic trial-control
builder. That builder is explicitly allowed to transform the trial, including
projection. The policy does not verify that the actual returned displacement
is $\tau d$. It accepts any returned update with a negative initial slope and
an objective no larger than the initial value plus tolerance.

Consequently a builder returning, for example,
$u+0.25\tau d$ on a positive quadratic is accepted even though it is not the
one-dimensional minimizer. The result still reports the unscaled $\tau$ as
its step length. The committed transformed-builder test covers Armijo only;
the exact-search test uses the identity builder and asserts objective
nonincrease rather than stationarity at the exact minimizer.

This also contradicts the roadmap statement that exact acceptance uses the
actual returned displacement. The actual displacement is inspected only for
descent; it does not determine or validate exactness.

### Required outcome

Give exact quadratic search a straight-line trial contract distinct from
projecting/backtracking builders, or validate that the returned displacement
is the computed scalar multiple of the nominal direction. Keep exact search
unavailable for projected trials until a separate constrained exact-search
meaning is selected. The accepted result's reported step must describe its
actual control update.

### Required tests

- independently verify $j_h'(u+\tau d)[d]=0$ on the quadratic target;
- reject or otherwise deliberately handle a scaled builder;
- reject a projected/transformed builder for the current selected scope;
- verify the reported step against the actual displacement; and
- retain missing-capability and non-positive-curvature diagnostics.

## P6.1-R6 – truncated-CG boundary steps can remain interior

**Severity:** P1 – the subproblem can report boundary or negative-curvature
termination without returning the required trust-region boundary step.

### Evidence

`make_boundary_subproblem()` correctly solves the quadratic equation for the
positive intersection parameter along the current CG search direction. It
then applies

```cpp
std::min(1.0, boundary_scale)
```

instead of applying the computed intersection parameter. There is no
mathematical reason for that parameter to be at most one: the search direction
is not normalized, and a valid intersection commonly has a parameter larger
than one.

For example, in one dimension with the identity metric, gradient magnitude
$0.1$, radius $1$, and positive Hessian $0.05$, the first CG search direction
has norm $0.1$, the unconstrained CG step crosses the radius, and the boundary
intersection parameter is $10$. The implementation clips it to $1$ and
returns a step of norm $0.1$ while reporting `boundary`. The same defect
affects the negative-curvature exit.

The committed boundary test uses radius $0.25$ on a direction for which the
intersection parameter is already below one. It therefore proves that one
case fills the radius but does not exercise the faulty branch.

### Required outcome and tests

Apply the actual positive boundary intersection, with a numerical tolerance
that verifies the resulting metric norm equals the current radius. Add tests
for:

- a boundary intersection parameter below one;
- a boundary intersection parameter above one;
- negative curvature with an above-one intersection;
- a nonzero current CG step before the boundary intersection; and
- actual/predicted reduction and radius-update diagnostics for those steps.

## P6.1-R7 – exclusive objective/step stopping fails at stationarity

**Severity:** P2 – the selectable stopping API has an unhandled initial/final
stationary edge case.

### Evidence

`ReducedStoppingCriterion::objective_change` and `step_norm` disable the
absolute-gradient stop. At an exactly stationary iterate, steepest descent
returns a zero direction. The solver checks the disabled gradient criteria,
then requires strict descent before an objective change or step exists and
before checking the maximum-iteration safety cap. It therefore throws a
generic non-descent contract error.

The trust-region solver has the analogous behavior: with the gradient stop
disabled, the Cauchy path requires a positive gradient pairing and the
truncated-CG path requires a positive initial residual pairing. A stationary
initial control cannot produce either selected post-step quantity.

The committed selector tests start away from stationarity and set very large
objective/step tolerances so that one accepted step triggers the selected
reason. They do not cover a stationary initial control or a stationary
iterate reached before the post-step criterion fires.

### Required outcome and tests

Specify the no-step outcome for criteria that are defined only after an
accepted update. A stationary iterate should return a typed stationary reason
or an explicitly documented safety reason, not a direction/subproblem
assertion. Verify the behavior for both line-search and trust-region solvers,
including a stationary initial point and stationarity reached after one step.

## P6.1-R8 – compiled Hessian exposure exceeds its verification

**Severity:** P2 – the implementation may be correct, but the roadmap's
per-path Hessian acceptance requirement is not met by the committed evidence.

### Evidence

`98d4e46` assigns the optional reduced-Hessian capability to every
`ScalarComponentModel` selected by `uses_assembled_v1_target`. That family is
broader than fixed-Dirichlet volume tracking: it also covers selected
subdomain, $H^1$, point-sensor, normal-flux, and general scalar
tensor/transport/Robin registrations. The general scalar branch can use a
nonsymmetric state operator and its transpose solve.

The new compiled-provider test checks symmetry and finite-difference action
only for the fixed-Dirichlet assembled target. The direct deal.II target has
its own corresponding test. No Hessian test invokes the other assembled
observation or nonsymmetric-residual paths even though they all expose the
capability. The roadmap's done condition requires every selected
Hessian-vector path to pass symmetry and finite-difference reduced-covector
tests.

### Required outcome and tests

Keep the capability optional per compiled target and add a compact coverage
matrix for every assembled path that receives it. At minimum, verify symmetry
and centered finite-difference action for representative volume/subdomain,
$H^1$, point-sensor, normal-flux, and nonsymmetric general-scalar operators,
plus capability absence for target families that do not provide it. If some
registrations are not intended to expose the Hessian, narrow assignment in
the compiler instead of relying on untested implementation sharing.

## Remediation handoff

Keep remediation separate from this historical review. A practical sequence
is:

1. gate projected solver compositions and exact quadratic trial semantics
   (`R1`, `R5`);
2. repair zero-step and exclusive-stopping outcomes (`R4`, `R7`);
3. correct truncated-CG boundary intersection and add scaled/negative-
   curvature cases (`R6`); and
4. close the callback and backend evidence gaps (`R2`, `R8`).

The next implementation-review batch is P6.2, beginning at `0533db2`. It
should be reviewed against the Chapter 6 benchmark-suite roadmap without
using any later P6.3 implementation to justify its state.

## Acceptance checklist

P6.1 cannot be accepted from the reviewed evidence until all open findings
are closed and the following checks hold:

- [x] only deliberately selected direction/line-search policies expose
      projection;
- [x] projected stopping uses the declared metric projected-gradient map;
- [x] BFGS metric-action reports equal independent inverse-metric callback
      counts;
- [x] Newton aggregate metric-action counts include both initial inverse
      applications and all PCG preconditioner actions;
- [x] Newton and truncated-CG inner tolerance convergence cannot return an
      unusable zero step to a nonconverged outer method;
- [x] exact quadratic search proves or enforces its straight-line exact step;
- [x] every boundary/negative-curvature truncated-CG exit fills the current
      metric radius;
- [x] objective-change and step-only stopping have a typed stationary
      outcome;
- [x] every compiled target that exposes a Hessian has symmetry and
      finite-difference evidence;
- [x] missing, incompatible, and non-positive-curvature capability paths keep
      stable diagnostics; and
- [x] the required neutral and deal.II verification profiles pass after
      remediation.
