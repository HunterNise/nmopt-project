# P6.1 implementation review and remediation handoff

## Status and authority

This document records the incremental review of the P6.1 implementation
commits after `codex/main` on 2026-08-16. The review currently covers the
inclusive history range `ff773d5` through `bddad18`. It stops before the
reduced line-search policy commit `0720102`.

This is static review evidence and a remediation handoff, not a second
capability ledger. The
[implementation roadmap](../../implementation-roadmap.md) remains the sole

[Chapter 6 numerical-methods guide](../../../guides/chapter-6-numerical-methods.md),

and [interface specification](../../../design/interface-specification.md)

The reviewed history establishes a useful typed direction-policy seam, a
correct linear-quadratic reduced-Hessian formula, and a metric-preconditioned
Newton-CG consumer. It is not acceptance-complete at the current review
boundary. The open findings are:

1. `P6.1-R1` – the shared solver publicly permits projected nonlinear-CG,
   L-BFGS, and Newton even though only projected steepest descent is selected;
2. `P6.1-R2` – L-BFGS action accounting is corrected by `bddad18`, but the
   focused regression evidence does not verify the correction;
3. `P6.1-R3` – Newton under-reports one inverse-metric action per direction;
   and
4. `P6.1-R4` – an allowed mismatch between inner absolute tolerance and outer
   stopping tolerance can return a zero Newton direction before the outer
   solver has converged.

Later P6.1 commits may remediate these findings. Their status must be updated
only after those commits are reviewed in historical order.

- a reduced direction is primal, while the reduced derivative remains a

## P6.1-R1 – unsupported projected advanced directions are public

**Severity:** P1 – blocks acceptance because the public solver boundary can
execute combinations that the Chapter 6 scope explicitly excludes.

### Evidence

`ReducedSearchSolverT` is templated on `DirectionPolicy`, but both of its
constructors are available for every policy. The second constructor accepts a
`ConstraintT` and enables projection. The public aliases for nonlinear CG,
L-BFGS, and Newton all reuse this same class:

- `ReducedConjugateGradientSolverT`;
- `ReducedLimitedMemoryBfgsSolverT`; and
- `ReducedNewtonSolverT`.

There is no policy capability check in the constraint-taking constructor.
Each alias can therefore be constructed with a box constraint even though the
roadmap and numerical-methods guide retain projected steepest descent as the
only selected projected direction.

The behavior is not merely unverified. In the constrained branch,
`evaluate_projected_gradient()` constructs

```math
u^{+}=\Pi_{U_{\mathrm{ad}}}(u+d)
```

from the policy's returned direction and uses $`u^{+}-u`$ as the stopping
residual. This agrees with the declared projected-gradient residual

```math
u-\Pi_{U_{\mathrm{ad}}}(u-G^{-1}j_{h}')
```

up to sign only when $`d=-G^{-1}j_{h}'`$. For nonlinear-CG, L-BFGS, and
Newton directions it is a different quantity and may report stationarity for
the wrong map. The committed projected tests instantiate only
`ReducedGradientSolverT`; they do not prove or reject the advanced aliases.

### Required outcome

The public API must make the selected projected boundary explicit. A bounded
repair may either:

1. make the constraint-taking solver constructor available only to the
   steepest-descent policy; or
2. give direction policies a typed projection capability and reject every
   unselected policy with an exact diagnostic before a solve begins.

Do not make projected nonlinear-CG, L-BFGS, or Newton appear supported by
changing only the stopping residual. Those methods remain excluded until
their active-set transition, restart, and metric-coupling contracts and tests
are deliberately selected.

### Required tests

- preserve projected steepest-descent convergence and the exact declared
  projected residual;
- reject constrained construction or execution for nonlinear-CG, L-BFGS, and
  Newton with one stable capability diagnostic each; and
- prove that adding a new unconstrained direction alias does not implicitly
  acquire projection support.

## P6.1-R2 – L-BFGS metric-action reporting lacked exact evidence

**Severity:** P2 – the implementation is corrected in the current reviewed
state, but its required solve-count evidence remains incomplete.

### Evidence

At `965ea21`, the solver incremented `metric_solve_count` once for every
direction evaluation. An accepted L-BFGS update actually invoked
`metric.inverse_apply()` twice: once in `make_metric_gradient()` and once on
the two-loop recursion's covector `q`. The report therefore returned $`n`$
for the common $`2n-1`$ inverse actions used by $`n`$ successive directions.

`bddad18` repairs the implementation shape. `ReducedSearchDirectionT` now
carries per-direction metric and Hessian action counts, the accepted L-BFGS
path returns two metric actions, and the outer solver accumulates those
reported counts. Initial and curvature-reset steepest directions correctly
return one.

The new tests do not use an instrumented metric and do not assert the L-BFGS
metric count after an accepted secant pair. They verify convergence,
monotonicity, history size for one pair, and reset reporting, so the count
repair remains unprotected.

### Required outcome and tests

Retain per-direction action accounting. Add an instrumented metric or another
independent oracle that proves:

- the initial L-BFGS direction reports one inverse action;
- a direction using an accepted secant pair reports two;
- a curvature-reset direction reports one; and
- the accumulated solver count equals the actual callback count.

Also exercise eviction at the configured memory bound and L-BFGS-specific
history-layout rejection; those declared behaviors are not covered at this
review boundary.

## P6.1-R3 – Newton under-reports inverse-metric actions

**Severity:** P1 – blocks acceptance because the uniform action report is a
declared P6.1 result and currently reports false work.

### Evidence

`NewtonDirectionPolicyT::next()` first calls `make_metric_gradient()`. That
helper invokes `metric.inverse_apply(reduced_derivative)` to compute the outer
metric gradient and norm. The Newton policy then negates the derivative and
invokes `metric.inverse_apply(residual)` again for the initial PCG
preconditioned residual.

Only after the second call does the implementation initialize
`metric_solve_count` to one. Every PCG iteration increments the count for its
next preconditioned residual, but the first inverse action used by
`make_metric_gradient()` is never included. For $`k`$ Hessian/PCG iterations,
the policy executes $`k+2`$ inverse-metric actions and reports $`k+1`$.

The test assertion
`metric_solve_count > hessian_action_count` cannot detect this error: both the
incorrect $`k+1`$ and the correct $`k+2`$ satisfy it.

### Required outcome

Count every inverse-metric callback exactly once. A repair may reuse the
already computed negative metric gradient as the initial preconditioned
residual, or retain the second callback and initialize the count to two. The
choice must preserve the typed primal/covector boundary and the declared
outer gradient norm.

### Required tests

Use an instrumented metric and independently count callbacks for:

- an immediately converged inner solve;
- a one-iteration PCG solve;
- a multi-iteration PCG solve; and
- an inner failure after at least one Hessian action.

The result's metric and Hessian counts must equal the independent callback
counts on both success and any returned failure report introduced later.

## P6.1-R4 – inner tolerance can yield a zero nonconverged outer step

**Severity:** P2 – an individually valid parameter combination reaches a
generic descent assertion instead of a deliberate Newton outcome.

### Evidence

The Newton policy defines the inner target as

```math
\max(\varepsilon_{\mathrm{abs}},
     \varepsilon_{\mathrm{rel}}\lVert j_{h}'\rVert_{G^{-1}}).
```

It initializes the Newton direction to zero and skips PCG when the initial
residual norm is already below that target. The returned direction then has
$`j_{h}'[d]=0`$.

The outer solver independently compares the same metric gradient norm with
its own `gradient_tolerance`. If

```math
\text{outer tolerance}
< \lVert j_{h}'\rVert_{G^{-1}}
\leq \text{inner absolute tolerance},
```

the outer stop does not fire, but the zero Newton direction reaches the strict
descent assertion and throws `Reduced gradient did not produce a descent
direction`. All three values are individually accepted by parameter
validation, and no diagnostic identifies the incompatible stopping policies.

### Required outcome

Define the relationship between outer stationarity and an inner solve that
requires no iteration. The solver must either:

- reject incompatible outer/inner tolerances before evaluation;
- report a typed inner-solve/stagnation outcome that the outer solver handles;
  or
- use a forcing policy that guarantees a meaningful direction whenever the
  outer criterion is not met.

Do not silently reinterpret inner convergence as outer stationarity.

### Required tests

- cover an initial residual below both tolerances;
- cover an initial residual below the inner absolute tolerance but above the
  outer gradient tolerance;
- verify the exact stop or diagnostic for that mismatch; and
- retain the ordinary positive-curvature Newton convergence case.

## Acceptance checklist

P6.1 cannot be accepted from the currently reviewed evidence until all of the
following are true:

- [ ] projected support is unavailable for every unselected direction policy;
- [ ] the projected stopping residual is the declared metric projected
      gradient residual;
- [ ] L-BFGS metric-action counts have an independent regression test;
- [ ] Newton metric-action counts equal the actual inverse-metric callbacks;
- [ ] inner and outer Newton tolerances have a deliberate compatibility or
      stagnation policy;
- [ ] the dense linear-quadratic Hessian finite-difference and symmetry checks
      remain passing;
- [ ] missing, incompatible, and non-positive-curvature Hessian paths have
      stable diagnostics; and
- [ ] the required neutral and deal.II verification profiles pass after any
      remediation.
